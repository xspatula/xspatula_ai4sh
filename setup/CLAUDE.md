# Audit system

Auditing is a generic, trigger-based system (not per-table shadow tables, not application code), driven automatically from an inline `"audit"` key that a `create_table` process block may carry — opt-in: no key (or an all-`false` one) means that table isn't audited. Coverage is verified by diffing `pg_class` against `pg_trigger`, not by reading the JSON config, since the two can drift.

- **`"audit": {"INSERT": bool, "UPDATE": bool, "DELETE": bool}`** — a sibling key next to `"parameters"` on a `create_table` block. `community`, `process`, `utility`, `observation_utility`, `landscape_utility` (low-volume: admin/config data plus reference/catalog tables like `indicator`, `taxa`, `apparatus`) get full `INSERT`/`UPDATE`/`DELETE`. `observation`, `landscape` (bulk pipeline-written data — samples, measurements, spectra) get `UPDATE`/`DELETE` only — auditing every `INSERT` there just doubles write volume on import batches with no real audit value, since the row's existence already proves creation. Follow the same convention for new tables.
- **`audit.logged_actions`** — one row per INSERT/UPDATE/DELETE on any audited table: `schema_name`, `table_name`, `op` (I/U/D), `old_data`/`new_data` as JSONB (full row image via `to_jsonb()`), `changed_by`, `changed_at`, `txid`.
- **`audit.if_modified_func()`** — single generic PL/pgSQL trigger function shared by every audited table. No per-table column list to maintain, so it can't drift when a table's schema changes.
- **Two-step, deliberately disentangled from core setup**: `setup/src_setup/lib_setup/setup_db_audit.py`'s `Assemble_audit_config()` is pure file I/O — no database connection — run automatically at the end of every `setup_db.ipynb` main-setup pass (from `Initiate_database`). It scans every `create_table` block reachable from the pilot list for its `"audit"` key and (re)writes the per-schema `setup/zzz/ai4sh/setup_db/json_ai4sh/audit/audit_triggers_<schema>_v10_sql.json` files (add/update/prune only — untouched schemas are left byte-for-byte alone) plus a generated pilot file, `setup/zzz/ai4sh/setup_db/db_xspatula_ai4sh_audit.txt` (auto-generated, not hand-maintained — always lists the 3 bootstrap files plus every schema with any currently-audited table, regardless of whether that schema's file changed this run — a table's DDL trigger creation must never be skipped just because its JSON already happened to be correct on disk). Applying that config to the database — creating `audit.logged_actions`, `audit.if_modified_func()`, and every trigger — is a separate, optional step: `Initiate_audit()` in `setup_db_initiate.py`, wired to its own notebook cell (`job_setup_audit.json` → the generated pilot file), reusing the same `Setup_schemas_tables` dispatcher the main setup uses. Running it is what opts a database into auditing at all; skipping it means no audit triggers exist. Two `process_id`s in `setup_db.py` support the underlying blocks: `execute_sql` (raw SQL, used once for the trigger function) and `create_trigger` (same exists-check/overwrite/delete semantics as `create_table`).
- **To audit a new table**: just add/confirm its `"audit"` key on the `create_table` block. Nothing else — the trigger config file, the pilot file, and (once the audit cell is run) the database trigger are all regenerated automatically on the next setup pass, regardless of where in the pilot list the table was added.
- **`audit.logged_actions` audits itself**, but `UPDATE`/`DELETE` only — never `INSERT`. `if_modified_func()` responds to every trigger event by inserting into `audit.logged_actions`; an `INSERT` trigger on that same table would make that internal insert re-fire itself, recursing infinitely. `_Collect_table_audit_state` in `setup_db_audit.py` silently strips `INSERT` from this one table's declared events as a hard-coded guard.
- **Read-only reporting access**: the `login_evaluation` role (`ROLES_D`/`REVOKE_D` in `setup_db.py`) has `USAGE` on the `audit` schema and `SELECT` on `audit.logged_actions`, alongside its existing SELECT-only access to `community`. Role grants are hash-checked in `Create_db_roles` and auto-reapplied whenever `ROLES_D` changes, so editing that dict is enough — no manual `GRANT` step needed on the next setup run.
